* Direction

Develop Emacs as the working environment for research, analysis and writing,
with Obsidian as the primary notes system. Prioritize a complete path from a
Zotero reference to a PDF, a literature note, a manuscript citation and a
source-linked research synthesis.

The two user decisions are settled: Obsidian should become the main notes
system, and the most valuable LLM use is research across selected notes and
papers. The proposed division of responsibilities is below. Retaining Org
for agenda, executable documents and repository documentation is now an
explicit requirement. A wholesale migration is outside scope.

analyze → write → verify → revise → validate → submit → archive. Reliability,
traceability and lower repetition take precedence over package count.

** P0b — pinned bootstrap, update and rollback

- Objective/problem/justification: make restoration independent of today's
  upstream package versions. This is the highest remaining P0 gate.
- State/modules/dependencies: VALIDATED locally; =init-core.el=, =awc-packages.el=, Straight recipes,

- Risks/alternatives: a revision list may omit local patches or untracked

  packages as though their HEAD alone reproduces them. Keep system binaries

  restore, clean representative builds and native thaw/rebuild pass. An HTTPS
  bootstrap smoke check passes. Full startup from restored sources exposed

  startup compilation, with native terminal validation still separate.
  Final checkpoint below records executed results and limits. Fast CI needs

  No installed source/package version or live research environment is upgraded.
- Rollback: preserve the prior installed package tree and lockfile; restore

** Shared fixture and completion rules

Extend the existing tiny synthetic reference/note/manuscript fixture as each
feature arrives: project → environment → cite/read/note → diagnostics →
analysis/render → evidence → feedback → checks/manifest → recovery. Keep
human acceptance separate from unit, Emacs integration and external-tool tests.

passes, close it; reopen only for a defect, regression, security issue,
changed dependency or evidenced workflow need, recording the reason.

* Zotero and citations

** First implementation

Adopt Zotero as the proposed metadata authority and Better BibTeX as the
export layer. Better BibTeX supports automatic library or collection exports
and controllable citation keys. Before redirecting existing bibliography
paths, reconcile their keys and any entries absent from Zotero, preserve a
snapshot, and test an export to a new path. Preserve established keys;
changing a key is a migration, not a metadata refresh. For Zotero 8 and later,
the current [[https://retorque.re/zotero-better-bibtex/][Better BibTeX migration notice]] describes native synced keys and
supersedes older advice about separately pinning BBT keys.
See [[https://retorque.re/zotero-better-bibtex/exporting/auto/][automatic exports]] and
[[https://retorque.re/zotero-better-bibtex/citing/][citation key handling]].

Use Citar as the Emacs entry point for reference search and actions. Its
existing support for Org, Markdown and LaTeX, and its configurable resource
and note interfaces, make it the natural place to connect Obsidian notes.
See [[https://github.com/emacs-citar/citar][Citar documentation]].

Required actions:

- Find references by author, title, year or key; insert the appropriate
  citation syntax for the current document.
- Open the Zotero item, choose an attachment, or visit/create its literature
  note. Repeated note creation should find the existing note.
- Respect project bibliographies and flag a selected item missing from the
  manuscript's bibliography. Make adding it a deliberate export operation.
- Report missing attachments, stale exports and ambiguous keys clearly.
  Existing bibliography-based citation insertion should work with Zotero closed.

Prefer bibliography files for the first citation path. Add a read-only local
Zotero API adapter when item or attachment lookup needs it; verify the
installed client's capabilities first. The official local API provides an
interface to the local library without opening its SQLite database directly.
See [[https://www.zotero.org/support/dev/web_api/v3/local_api][Zotero local API documentation]].

Retire or replace =sync-ebib-to-zotero= once this direction is implemented.
Keep Ebib for explicitly owned project bibliographies if useful; editing a
generated Zotero export must not be presented as a durable library update.

** PDF reading and annotations

Support PDF Tools for reading in Emacs and an action to open the source in
Zotero. Choose one annotation authority before adding annotation import;
Zotero is the proposed default. Validate export of selected annotations with
page references into a literature note. Do not assume PDF Tools highlights
and Zotero annotations synchronize automatically.

Acceptance fixtures should include multiple attachments, a missing local

* LLM integration for research

** Scope and interface

The first product should answer a bounded research question over sources
chosen by the user. Example: select three papers and two notes, ask how their
definitions differ, inspect the cited passages, and save a reviewed comparison
as an Obsidian note.

Use gptel as the first client candidate. It already exists here and documents
selected context, multiple backends and reviewable edits. Its added context
is normally live and can be global, so a research workflow needs explicit
session ownership and a record of the text actually sent. Verify the installed
package API before configuring against current examples.
See [[https://github.com/karthink/gptel#usage][gptel usage and context documentation]].

The research integration should supply the following behavior:

1. *Select sources.* Choose vault notes, Citar references and optional text
   selections. Display the source list, model/backend and included passages
   before sending. Opening a note must not send it anywhere.
2. *Prepare evidence.* Extract selected PDF text with page boundaries and
   note text with heading anchors. Flag scans requiring OCR and poor reading
   order; tables, equations and figures may require separate inspection.
3. *Bound the context.* Send complete selected sources when they fit. For
   larger selections, offer local passage search within that selection and
   show what is included. Make omissions and truncation visible.
4. *Answer with provenance.* Require source identifiers and locators for
   substantive source claims; distinguish quotation, paraphrase and inference.
   Explain when the selected material does not answer the question.
5. *Inspect and save.* Clicking a source opens the note heading or PDF page.
   Save a synthesis only through an explicit action, with question, source
   list, date, backend/model and review status. Applying changes to an existing
   note should show a diff.

Citation keys and bibliography entries must come from the selected records.
The model must not invent them. Citation presence alone does not establish
that a passage supports a claim; the interface must make that check easy.

** Architecture and limits

Keep source preparation separate from the model client. A local evidence
record should include source identity, path, source revision or content hash,
locator and extraction method. Use PDF page index as a reliable locator,
recording printed page labels separately when known. Cached extracts and
indexes are disposable; edits, replacement PDFs and deletions invalidate them.

Keep each research session's source selection isolated. Before adding files,
resolve paths against the selected vault/library scope. A note's links or
instructions inside a paper must not expand that scope or trigger commands.
The pilot needs no shell, filesystem-write or library-write tools for the model.
Credentials belong in an environment or credential store, not saved notes.
Retain only the request content/history the user chooses to keep.

| Approach | Role in this roadmap | Adoption condition |
|----------+----------------------+--------------------|
| Selected sources in gptel | First pilot | Source previews, isolation and usable citations |
| Local passage search over selected sources | Add when context is too large | Measured improvement over manual source selection |
| Embeddings and wider library retrieval | Later experiment | Evidence that lexical search misses useful material; tested indexing and deletion behavior |
| Autonomous project or library agent | Deferred | A separate use case and review model justify broader actions |

Choose a hosted or local backend using the same research questions. Compare
source fidelity, latency, context capacity, operating effort and cost. A
hosted pilot needs a decision on which materials may leave the machine; a
local pilot needs a hardware and model-quality check. No provider or model is
selected by this roadmap. Set context/output limits and expose usage when the
backend reports it; do not imply a precise cost when it is unavailable.

** Pilot acceptance

Use roughly 5–10 papers and associated notes, with a small fixed question set:
a factual lookup, a definition comparison, a disagreement between sources,
a question the sources cannot answer, and a synthesis requiring several papers.

- Every displayed source link resolves; sampled claims can be checked against
  the exact supporting passage. Unsupported claims and misleading omissions
  are recorded during review.
- Excluded sources stay excluded, and one session never inherits another's
  context. Source edits visibly invalidate cached evidence.
- Missing PDFs, poor extraction, excessive context, cancellation and backend
  errors produce understandable recovery paths without overwriting notes.
- Record time to a usable answer, manual correction effort and usage/cost
  where available. Expand only if the pilot improves the actual workflow.
